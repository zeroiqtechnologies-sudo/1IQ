# SetuHomes — Pune developer project & CP lead marketplace (prototype)

A runnable, responsive **web** prototype of an Indian real estate marketplace where:

- **Developers** list projects (admin approval required before they're public).
- **Customers** discover projects, compare, shortlist, enquire with explicit consent, and track their enquiry.
- **Admin** verifies companies/partners, moderates listings, qualifies enquiries, previews matching, runs auctions and reviews disputes.
- **Channel partners (CPs)** follow projects, bid for anonymised qualified leads from a prepaid balance, and the single winner manages follow-ups and site visits.

> **Demo mode.** Everything runs in the browser with deterministic simulated services and `localStorage`. No backend, no paid API keys, no real payments, OTP, calls, SMS, WhatsApp or email. Role switching is **not** secure authentication, and there is no real multi-user concurrency. "SetuHomes" and every developer, project, partner, person, phone number and registration number is fictional.

## Run it

Requires Node 18+ (tested on Node 22).

```bash
npm install
npm run dev          # http://localhost:5173
npm test             # 30 business-rule & persistence tests (Vitest)
npm run build        # type-check + production build into dist/
npm run preview      # serve the production build on http://localhost:4173
npm run build:single # one self-contained dist-single/index.html (hash routing), opens without a server
```

Use the yellow **DEMO MODE** bar at the top of every page to switch persona, see the demo clock (IST) and reset data.

All steps are also listed with links at `/admin/demo`.

2. **Admin publishes** — Admin → Listings → Mark reviewed → Approve & publish.
3. **CP shows interest** — Sameer (and Aditi) → Projects → Mark Interested.
4. **Customer enquires and consents** — Guest → project page → Enquire → tick the (unticked by default) consent → OTP `123456`.
5. **Admin qualifies and previews matching** — Admin → Qualification → open enquiry → confirm checks → Qualify lead (matching + per-CP eligibility shown).
6. **Admin starts the auction** (configurable start / increment / duration).
7. **CP tops up and bids** — Sameer → Wallet → Add ₹1,000 (success or failure) → Auctions → Place bid (dialog shows balance impact).
8. **Another CP outbids** — switch to Aditi and bid, or use "Bid min" on the admin auction page / Demo controls.
9. **CP rebids** at the new minimum.
10. **Demo clock closes the auction** — Admin → Demo controls → +10 min.
11. **Winner is charged once and sees contacts; loser's hold is released** — Sameer → My leads; Aditi → Wallet ledger.
12. **Winner adds a follow-up and site visit**, moves CRM stages, can report an invalid lead.
13. **Admin reviews the dispute** — Admin → Disputes → Approve (one refund credit) or Reject (no balance change).

## Business rules implemented

- Only **approved, active** CPs with an **Interested** record on a matched project can bid; optional per-project developer approval is respected. Ineligible CPs see the reason.
- Enquiries are never auto-qualified: `received → verification pending → qualification pending → qualified / rejected / duplicate / withdrawn`. Only qualified enquiries with active consent can be auctioned.
- Project-specific enquiries stay with their project; alternatives only with customer permission. **One enquiry → one auction**; an assigned enquiry is never resold.
- Auction previews are built from an allow-list (`toAuctionPreview`) — no name, phone, email, address, free-text notes or internal admin notes. Contacts are only returned by `readPurchasedContact`, which checks the assignment owner; access is audited.
- **Admin owns auction setup.** Only an admin can set the default rules, start an auction (optionally with its own opening bid, increment and duration), cancel it or retry a failed settlement; CP, developer and customer actors are rejected in the domain layer. CPs see the rules read-only and can only bid on and buy leads.
- Defaults (configurable by admin, validated, copied onto each auction): ₹500 start, ₹100 increment, 10 minutes, first-price, no extension.
- Rejects late (at or after close), below-minimum, off-increment, ineligible, suspended and insufficient-funds bids. Ties go to the earliest accepted sequence (a later equal bid is rejected with the new minimum).
- Holds: full leading bid held; a leader raising holds only the difference; an outbid CP's hold is released in the same operation as the new leader's reserve. Available = total − all active holds, across auctions. Money is integer paise.
- Settlement is exactly-once and idempotent (`settle:<auction>` ledger key): consume hold, debit, one purchase + receipt, one assignment. Losers pay nothing. No-bid auctions expire with no debit. Cancellation and pre-settlement consent withdrawal release holds. Settlement failure goes to admin review — never to the runner-up.
- Top-ups simulate success/failure; duplicate gateway callbacks are ignored. No withdrawals or transfers.
- Refunds require admin approval and create one separate, auditable credit (idempotent by purchase); purchases are never edited; rejections don't move money.
- Duplicate phone numbers are flagged for review; admin can clear a legitimate repeat.

## Architecture

```
src/
  domain/          Pure, typed business logic (no React)
    types.ts       Data model (all money in paise, times in epoch ms)
    auction.ts     start / placeBid / settle / cancel / closeDueAuctions
    wallet.ts      balances, simulated top-ups, ledger, adjustments
    enquiry.ts     submission, OTP, duplicates, qualification, consent withdrawal
    eligibility.ts CP eligibility + deterministic project matching
    projects.ts    developer/listing/CP-profile/interest operations with ownership checks
    crm.ts         stages, notes, reminders, visits, disputes & refunds
    views.ts       masked auction previews, purchased-contact access, metrics
    demo.ts        demo-only controls (simulated bidder, seed enquiry, end now)
  data/seed.ts     Deterministic seed built by running domain operations
  services/
    interfaces.ts  Replaceable ports: Clock, Auth, PaymentGateway, Otp, Messaging, Realtime, Repository
    local.ts       Local implementations: localStorage repo, transactional `tx`, demo clock,
                   settlement worker, simulated gateway/OTP, cross-tab sync via `storage` events
  state/hooks.ts   React bindings (useDb, useSession, useNow, useAct)
  ui/              Design kit (buttons, badges, dialogs, searchable/paginated tables, toasts) + generated visuals
  layouts/         Public site layout; portal layout with sidebar (desktop) / compact menu (mobile)
  pages/customer|cp|developer|admin
```

Every state change runs through `tx()`, which applies the operation to a cloned draft and commits only if it doesn't throw — the in-browser stand-in for a database transaction. UI code never mutates state directly.

Routes: `/`, `/projects`, `/projects/:id`, `/compare`, `/shortlist`, `/enquire`, `/my-enquiries(/:id)`, `/partners`, `/cp/*`, `/developer/*`, `/admin/*`.

Stack: React 18, TypeScript (strict), Vite 5, Tailwind CSS 3, React Router 6, lucide-react icons, Vitest. Property images, floor plans and the locality map are generated SVG illustrations (no external or third-party assets).

## Simulated vs production-ready

| Area | In this prototype | Needed for production |
|---|---|---|
| Auth & permissions | Demo role switcher; checks in domain functions | Server sessions, server-side authorization on every API, audit of admin access |
| Data | One JSON document in `localStorage` per browser | Relational DB with transactions, row-level ownership, migrations, backups |
| Concurrency | Single browser; cross-tab refresh only | Atomic bid sequencing in the DB (e.g. `SELECT … FOR UPDATE`), idempotency keys, realtime over authenticated websockets |
| Time & settlement | Browser timer + adjustable demo clock | Authoritative server time and a server-side closing/settlement worker |
| Payments | Simulated gateway with success/failure and duplicate callbacks | Real gateway, verified webhooks, reconciliation, tax/invoicing and regulatory review of prepaid balances |
| OTP / messaging | Fixed code `123456`; call/message are logged previews | SMS/WhatsApp/email providers, rate limiting, consent-aware templates, DND compliance |
| Contact privacy | Allow-listed preview objects and an owner-checked accessor | Private contact store separate from requirement data, field-level encryption, API/export/notification masking |
| Documents & media | File names only; generated illustrations | Private object storage, virus scanning, real photography with rights |
| Registration checks | Admin marks "reviewed" manually | Registry integration and documented verification procedure |
| Production-ready as-is | Typed domain rules and their tests, UI flows, responsive layouts | — |

Commercial terms, lead exclusivity, refund windows, qualification standards, consent/retention and tax treatment are proposed defaults that need business and legal validation. This prototype makes no claim of legal compliance.
